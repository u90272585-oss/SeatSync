# SeatSync: как показать и объяснить backend

## Запуск

Открой терминал именно в папке проекта, где лежит package.json.

```sh
cd /Users/uldanatolegenkyzy/Documents/ChatGPT/startup2
npm ci
npm start
```

Открой http://127.0.0.1:3000/. Терминал должен оставаться открытым.
`npm ci` нужен при первом запуске или после изменения зависимостей; для обычного
повторного запуска достаточно `npm start`. Python-сервер больше не подходит для API.

Чтобы создать администратора, открой второй терминал в той же папке и выполни
`npm run admin:create`. Придумай email, имя и пароль от 10 символов. Пароль виден при
вводе в терминале — сделай это до демонстрации. Затем войди через Sign in на сайте.
Самостоятельно выбрать права администратора при регистрации нельзя.

## Что изменилось

Раньше данные сохранялись только в браузере. Теперь браузер отправляет запрос серверу,
сервер проверяет его и сохраняет бронь в SQLite. Администратор в другом браузере
получает ту же запись. Это работает только когда оба браузера открывают один сервер.
Публичный доступ с другого компьютера появится после размещения на хостинге.

Настоящие платежи и передача брони в кафе не подключены. Общая база и авторизация
работают внутри учебного проекта.

## Где что искать

- `server/index.cjs`: начало работы — открыть базу, запустить сервер на порту 3000.
- `server/database.cjs`: CREATE TABLE создаёт таблицы users, sessions, venues, tables,
  bookings. IF NOT EXISTS сохраняет существующие данные при повторном запуске.
- `server/app.cjs`: POST /api/bookings создаёт бронь, PUT изменяет её, маршрут
  /cancel отменяет. GET отдаёт данные. Функция owns проверяет владельца или админа.
- `server/auth.cjs`: пароль превращается в хеш с индивидуальной солью. При входе
  сравниваются хеши. Открытый пароль не записывается в базу.
- `js/api.js`: fetch отправляет запрос; await ждёт ответ. При ошибке показывается
  сообщение, а не ложное подтверждение.
- `js/booking-storage.js`: единый интерфейс для запросов брони. Массив records —
  временная копия для отображения. Главные данные находятся на сервере.
- `js/booking.js`: запрашивает свободные столы и отправляет заполненную форму.
- `js/confirmation.js`: получает сохранённую бронь по ID; кнопка Cancel отправляет
  запрос на сервер, а затем обновляет страницу полученным ответом.
- `js/admin-bookings.js`: заполняет существующие элементы дизайна Малики данными
  сервера. Каждые пять секунд повторяет запрос, пока вкладка видима.
- `js/account.js`: вход, регистрация, профиль, список бронирований.

## Как доказать, что это backend

1. Открой сайт в обычном браузере как клиент и в другом браузере как администратор.
2. Создай бронь на будущую дату. Покажи ту же запись в админке (до пяти секунд).
3. Попробуй выбрать тот же стол на пересекающееся время: он недоступен.
4. Измени бронь. ID остаётся прежним, админка получает изменения.
5. Отмени бронь. Запись остаётся со статусом Cancelled, стол освобождается.
6. Перезапусти сервер. Бронь всё ещё находится в базе.
7. Покажи `npm test`: тесты используют отдельную временную базу.

## Вопросы преподавателя

**Что такое API?** Адреса сервера, через которые интерфейс получает и изменяет данные.
Например, POST /api/bookings создаёт бронь.

**Зачем серверная проверка, если форма уже проверяет поля?** Браузер можно обойти.
Сервер независимо проверяет дату, время, гостей, вместимость и право доступа.

**Как предотвращается двойная бронь?** Проверка пересечения и сохранение идут внутри
одной транзакции BEGIN IMMEDIATE. Для одного заведения и стола учитываются активные
брони той же даты. Две заявки не могут одновременно пройти эту проверку.

**Что такое пересечение?** Начало старой брони раньше конца новой, а конец старой
позже начала новой. Если одна заканчивается ровно в момент начала другой, конфликта нет.

**Почему отмена не DELETE?** История нужна клиенту и администратору. Меняется status,
а при проверке занятости учитываются только confirmed записи.

**Зачем version?** Чтобы старая вкладка не перезаписала более новое изменение.
Если версия не совпадает, сервер просит перезагрузить страницу.

**Как сервер узнаёт пользователя?** По случайному токену сессии в HttpOnly cookie.
В базе хранится хеш токена. Роль администратора берётся из базы, а не из формы.

**Как работает гость?** Его записи связаны с текущей серверной сессией. При регистрации
или входе в том же браузере они прикрепляются к аккаунту.

**Где база?** По умолчанию data/seatsync.sqlite на компьютере сервера. На хостинге
нужен постоянный диск. Файл базы не отправляется в GitHub.

**Это уже production?** Это работающий учебный backend. Публичное размещение ещё
отдельный шаг; платежей, связи с реальными кафе и восстановления паролей пока нет.

## Короткое выступление на английском

My contribution connects the booking and confirmation flow to a real backend.
I use Node.js and Express for the API, and SQLite to store accounts and bookings.
When a customer confirms a booking, the server validates the data, checks table
availability and saves the reservation. The administrator can see the same booking
from another browser. Customers can edit or cancel their reservations. Cancellation
preserves the history and makes the table available again. The server checks access
permissions and prevents overlapping reservations. I kept our existing frontend
design and tested the complete flow. Payments and real restaurant integrations are
still outside this university prototype.

Используй это выступление после того, как сама разберёшь соответствующие функции.
На защите важно честно объяснять использование AI и собственное понимание кода.
